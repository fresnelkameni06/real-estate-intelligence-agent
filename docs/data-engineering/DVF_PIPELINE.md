# DVF Data Pipeline — Paris 2021–2025 (Phase 2.1)

Production-quality ETL for Paris residential DVF transactions.

## Scope

Department **75 only**, years **2021–2025**, from the geo-DVF source:

    https://files.data.gouv.fr/geo-dvf/latest/csv/{year}/departements/75.csv.gz

France-wide files are never downloaded. The DPE pipeline, PostgreSQL, API, UI,
RAG and orchestration are **out of scope** for this phase.

## Residential V1 scope

The main residential dataset keeps only:

- `nature_mutation == "Vente"`;
- `type_local ∈ {"Appartement", "Maison"}`.

VEFA, exchanges, adjudications and land sales are **excluded** from the V1
residential dataset; their counts are reported. Dependencies (parking, cellar,
storage) do **not** disqualify a residential mutation.

## Modules

- `src/real_estate_agent/ingestion/dvf/downloader.py` — idempotent acquisition
  with a manifest, atomic `.part` → `75.csv.gz` rename, gzip validation, SHA-256.
- `src/real_estate_agent/processing/dvf/transformer.py` — explicit-UTF-8 load,
  typed identifiers, schema/encoding validation, lineage, exact-duplicate
  handling, residential component table, mutation-level reconstruction,
  price/m² eligibility.
- `src/real_estate_agent/processing/dvf/quality.py` — per-year and global metrics.
- `scripts/run_dvf_pipeline.py` — orchestration and output writing.

## Idempotent acquisition

For each year the downloader builds the exact department-75 URL, follows
redirects (the source 302-redirects to OVH object storage), streams to a
temporary `.part` file, validates it is a readable non-empty gzip, computes the
SHA-256, then atomically renames it to `75.csv.gz`. A `manifest.json` records,
per year: source year, URL, local path, acquisition timestamp, content length,
last-modified, compressed size and SHA-256.

On a second run a file is reused only when it exists, is a readable gzip, and its
checksum matches the manifest. Because the source uses a moving `latest` URL, the
strategy is **manifest-driven** — no permanent hardcoded checksum. A valid raw
file is never modified silently.

## Grain and the key correction

One raw row is **not** one transaction. A mutation (`id_mutation`) can span
several rows (lots, dependencies, several dwellings, commercial units), and
`valeur_fonciere` is carried at **mutation grain** (never summed across rows).

`residential_unit_count` is the number of residential component **rows** per
mutation after exact-row deduplication — **not** `nunique(type_local)`. Two
`Appartement` rows are two units even though the type label is identical.

## Outputs

- `data/processed/dvf/dvf_residential_units.parquet` — one row per residential
  component (no full address fields; lineage attached).
- `data/processed/dvf/dvf_residential_mutations.parquet` — one row per
  residential mutation, with reconstructed counts, consistency flags, price/m²
  eligibility and `price_per_m2_raw`.
- `data/processed/dvf/dvf_quality_report.json` — machine-readable metrics.
- `docs/data-engineering/DVF_QUALITY_REPORT.md` — human-readable aggregates
  (generated by the run; never contains addresses or individual transactions).

Raw and processed data files are git-ignored; only code, tests and Markdown are
tracked.

## Price/m² eligibility

A mutation is eligible for a **raw** price/m² only when: it is a `Vente`, has
exactly one residential unit, a positive and consistent mutation value, a
positive residential surface, a valid date, and a valid unambiguous
arrondissement (1–20). Dependencies are allowed. `price_per_m2_raw =
mutation_value / residential_surface`. Outliers are **not** removed yet — the
full quantile distribution (min, P0.1…P99.9, max) is reported so the Project
Manager can choose the final outlier strategy.

## Run

```powershell
py scripts/run_dvf_pipeline.py   # first run: acquires + processes
py scripts/run_dvf_pipeline.py   # second run: reuses raw files (idempotent)

py -m pytest
py -m ruff check .
```

The pipeline exits non-zero if a required column is missing or French category
values are corrupted for any year.
